What a source must declare to appear as a room

Two declarations, one per direction. The read side is already the shape every connector normalizes to; the write side is the capabilities.communicator object the governed-send program defined (secretary-personal-agent/delivery/CONTRACT.md:14: a single object {ops, addressing}, never a boolean). A source that declares only the first is a read-only room (a meeting, an ads report, a ClickUp card). A source that declares both is a room you can also reach.

How the match works, and its honest failure mode

No vector search exists for skills today — verified, not assumed

Checked the schema and the codebase before designing around it. skill.schema.ts has no embedding field. common/vector/embeddings.ts is a real, reusable embed() helper (OpenAI/OpenRouter, used today for people/interaction semantic search into Weaviate) — but there is no Weaviate class or Mongo vector index for skills. Building one is possible, but it's new infra this seed didn't ask for and the SEED's own binding rule ("one reflection pass, not two") argues against growing a second subsystem to serve a match step that, at today's volume, doesn't need it.

What's proposed instead, sized to today's volume (≈26 skills on fernando-ott, one Space at a time): fetch every skill in the drafting persona's Space (name + description + topics — cheap, ~26 short rows, not the full 51KB instructions body) and hand the whole set plus the draft to the SAME reflection LLM call as a fifth field's context, asking it to classify: new / amend <skill_id> / duplicate <skill_id>. No new subsystem, no second call, scales fine into the low hundreds of skills per Space before token cost forces a cheaper pre-filter (keyword/topic overlap first, LLM only on survivors).

The failure mode, stated plainly

A too-eager matcher buries a genuinely new skill inside an amendment to an unrelated one.

The LLM is judging semantic closeness with no ground truth to check against. "Send a WhatsApp message" and "schedule a WhatsApp reminder for later" share enough surface vocabulary that a loose matcher folds the second into an amendment of the first — and because amendment approval mutates a LIVE skill in place (not a fresh inert row), that mistake is worse than the loose-threshold noise problem v1 already flagged: it doesn't just clutter Mission Control, it can quietly rewrite what an existing, already-relied-on skill does, on a persona a human never meant to touch.

Mitigation carried into the card itself, not just the matcher prompt: the amendment card (§3) always shows the diff and always names which persona(s) the target skill is already attached to — so even if the matcher is wrong, the reviewer sees "this claims to be an amendment to a skill already live on 1 persona" before approving, not after.

What DOES exist, and why it doesn't close the gap

There is a list_skills / get_skill reader pair (chat_skill_tools.py, registered as DEFAULT_GRANT in allow_set.py — meaning almost every persona already has it available regardless of its own skillIds).
