hermes-studio-layer

docs/implementation/hermes-studio-layer/SEED.md · 323 lines · seeded 2026-09-03
Plan · L · ~2 waves
What it does

Four screens that compose runtime Engine already has, filed as one seed by your ruling because they are one product decision.

  • S1 Conversas / Salas: a rooms list grouped by client org, the existing thread drawer in the centre, and a right pane with who is in the room and what the brain learned there (pending extracted_object proposals, approve inline).
  • S2 Conexões: one page with four chips (Dados, Canais, Ferramentas, Modelos) over the six connection-shaped nav rows, five of which hide under "Development" today.
  • S3 Plano: widen the squad admission object from goal + budget into steps + an acceptance checklist, and refuse "completed" while any item is red.
  • S4 Agent identity: a principal grammar agent:<space>/<slug> accepted by the ledger, proposal reviewer and admission decider, set at execute time from the bearer's agent slot.
Why it exists

Leo built a Studio layer by hand over Hermes and Fernando wants the equivalent over Engine's governed runtime. Two of the four became urgent in the last two weeks: the Secretário now sends real WhatsApp messages, and every one of those rows is attributed to the service brain-agent, not the persona. In the interactions feed an agent send is indistinguishable from Fernando typing on his phone.

Do we need it

S4: yes. It closes a live attribution defect and is the fact S1 and S3 both need to render honestly. It depends on the origin slot from governed-send R3-1, which merged on brain-agent as PR #151. That precondition is met.

S2: yes, and it is the cheapest visible win. Pure information architecture over existing endpoints. Zero dependencies.

S3: real, but the smallest honest cut is enough. The fence, the spend gate and the human checkpoint already exist. What is missing is a plan object with steps and acceptance. Leo's "20 use cases" is a development practice (plan-it test contracts), not a runtime object Engine lacks. Recommend hand-declared acceptance lists, no LLM, no canvas, in v1.

S1: needed, but its centre pane for group rooms has nothing to render until G-4 is decided. The seed already says so. A DM-only first cut can start once S4 lands.

Plan-it must decide
  • G-4 store-or-wall at this plan's gate (see seed 7). Recommended.
  • Decision G: personas per Space (recommended) or per client.
  • The noun. "Conversas" is already Modo Simples' label for the AI chat row. Recommend "Salas".
  • Principal grammar: slug (readable in an audit row, recommended) vs persona id.
  • Plan scope: every squad definition (recommended) or render-bearing only.
  • S2 default: move the five dev- rows to picker-only for all tenants (recommended; the overlay tombstone rule makes it safe).
Depends on

governed-send E1 (identity plumbing at the send; reuse, never re-plumb) · G-4 for S1 groups · secretary R3-5 (sticky re-entry, open) for the room to show a live loop · two sidebar registries (api-core + admin-ui mirror) must move in one PR.

Verdict

Plan it, as the anchor package of this cycle. Order inside the plan: S4 first, S2 in parallel, S3 third, S1 last. Put G-4 and decision G at the G2 gate so S1 is not planned against an unmade privacy call.

2 · Governance as a feature

agent-proposes-skill

docs/implementation/agent-proposes-skill/SEED.md · 219 lines · commissioned 2026-09-03
Plan · M
What it does

The reflection pass that already turns a finished run into flat facts and typed ontology candidates gains a fourth output: "was there a repeatable procedure here?" When it fires, the agent drafts a SKILL.md and files it as a skill_proposal ChangeProposal. On approve, a Skill row is minted with sourceType: agent-proposed, active but inert: attached to nothing, granting no tools, until a human attaches it through the existing governed chat tools.

Why it exists

Hermes learns procedures from its own runs. Engine's answer is to gate that learning the same signed way it gates spending money. The P16 ruling from drain 08-29 bound it to N3's reflection seam and forbade a second post-run pass. N3 shipped 08-31 with the seam live and instrumented on fernando-ott, which is why the seed was written now.

Do we need it

It is commissioned, and the plumbing is cheap. Seven gaps, all of the same shape N3 already closed for extracted_object: a new proposal kind, an approve branch, a card copy case, a provenance enum, a ledger key.

The value is entirely in one decision the seed cannot make: what counts as "worth proposing". Ask the LLM to judge every qualifying run in isolation and Mission Control fills with one-off "skills" nobody wants, which is the board-you-learn-to-ignore failure. A cross-run repeatability signal is the right detector but needs a tool-sequence store that does not exist, which pushes the size to L.

Cost is now measured on fernando-ott (last 14 days). 83 triggered runs, 55 passed the reflection gates, 861 memory rows written, 217 memory.capture ledger rows. The reflection call runs on openai/gpt-4o-mini through the Space's OpenRouter key. A fourth JSON field on that call adds roughly 50 to 80 tokens per run; a second call would add a whole prompt. Decision #1 is answered by the data: fold in.

No tool-sequence store exists. The runs collection does not persist tool calls, so a cross-run "same procedure seen N times" detector needs new schema. That confirms the seed's L-size warning for that path.

Plan-it must decide
  • Fold the fourth field onto the existing call (recommended, measured) vs a second call. Confirm recall on the other three streams does not degrade.
  • The proposing threshold (the load-bearing call).
  • Approval bar: confirm-tier at minimum, since no human asked for the skill.
  • Draft body on the proposal payload (recommended) vs a staging collection.
  • Ledger key: new skill.propose (recommended) vs widening memory.capture.
Depends on

Nothing unshipped. Rides N3's seam, the ChangeProposal fence, the card producer and the kind-agnostic chat approve/reject tools as-is.

Verdict

Plan it, second in priority. Insist the plan opens with a measured qualifying-run count and a same-run heuristic in v1 (0 or 1 candidate per run, own flag, default OFF everywhere). Defer the cross-run store to its own epic only if the v1 proposal stream proves noisy.

self-serve-first-run

docs/implementation/self-serve-first-run/SEED.md · 215 lines · seeded 2026-09-03
Plan · M
What it does

A registration endpoint pair that creates a User and a fresh Space atomically inside an existing tenant, seed-on-register (default backbone, default agent), a first-run wizard route, and abuse controls (invite code, rate limits, per-Space spend cap). Shape (a) in the seed: new Space, not new tenant. No terraform, no new database, no operator keystrokes.

Why it exists

Hermes installs with curl | bash. Engine has no public account creation anywhere: every user after the first is created by an admin calling a guarded endpoint by hand. N6 was the last un-ruled item of hermes-research, seeded with no design constraint.

Do we need it

This is a product question before it is an engineering one. Every tenant to date was created at sales-cycle speed by you or an operator, and the seed's own history says shape (b), tenant-per-signup, has never once been exercised. Self-serve Spaces only pay off if there is a motion for strangers signing up. If there is not, the (c) half alone, an in-Space onboarding wizard for a user an admin already created, still has real value for onboarding new clients on existing tenants.

The seed's hardest constraint is already solved. It calls byo-subscription "designed, frozen, nothing built" and makes it a hard precondition. The byo-subscription board says 8/8 epics VERIFIED, 103 of 107 cases green, the settings surface deployed to fernando-ott, and the package archived to 0-done. The planning gate should size against the real state, not the seed's.

The one genuinely new attack surface is real. Public account creation on a system that provisions LLM spend and a governed-actions fence needs the same review discipline as the SSRF and secret-blind-refs work. Invite-code only, fernando-ott only, in v1.

Plan-it must decide
  • Whether Engine wants a self-serve motion now, or only the in-Space wizard. G1 question.
  • Registration gate: invite code (recommended) vs public vs domain allowlist.
  • Hosting tenant: fernando-ott behind invite code; a dedicated tenant if the gate ever loosens.
  • Default agent identity for a fresh Space.
  • Email verification: no outbound email exists today; defer behind the invite code.
  • Space deletion for abandoned signups: nothing exists at Space granularity.
Depends on

byo-subscription (built; confirm the four gated cases do not touch registration) · a decision on outbound email (G4) · the governance fence stays on by default.

Stale factThe seed's effort estimate and decision #2 both assume byo-subscription is unbuilt. It is built and verified. The plan-it run must correct this in its findings doc before sizing.
Verdict

Plan it, with the product question first. If the answer at G1 is "not a self-serve motion yet", downscope to the wizard (shape c) and keep the registration pair as a later wave.

4 · Hygiene · locked flag-only

org-attribution-reconciliation

docs/implementation/org-attribution-reconciliation/SEED.md · 45 lines · promoted 2026-08-31 (G-5)
Plan light · S
What it does

A sweep that reads every interaction (and possibly persons and chat mappings), asks the org resolver what it would produce today, and reports rows where the stored organization_id differs. It never writes. Where the report lands (notifications, master-admin) and how often it runs are open.

Why it exists

Two root causes of misattribution were fixed on 08-30 (api-core #299, connectors #80). Those stop new drift. Nothing re-validates the existing corpus or catches future regressions: no cron in api-core and no script in brain-scripts touches attribution. Your ruling locked it to report-only because silently rewriting org ids has business blast radius.

Do we need it

Measured today: zero drift. On fernando-ott all 8,408 interactions carry an org id with no null, no person-to-interaction disagreement and no chat-mapping disagreement. On praxya the same holds across 45,147 interactions. The two 08-30 fixes did their job and nothing has regressed since.

The sweep is not free either. The resolver's resolve() unconditionally memoizes aliases and registers integration bindings on every call (org-resolver.service.ts:206,210). A "read-only oracle" needs a read-only variant of the resolver, or accepts idempotent writes on a sweep that was ruled report-only. That is design work for a problem that currently has zero rows.

The residual risk is small and named: 32 phones on fernando-ott match more than one person. The deterministic tiebreak (oldest person wins) handles them today; if the resolver ever regresses, those 32 are the rows that would drift first.

Plan-it must decide
  • Confirm the resolver is deterministic and side-effect-free when invoked read-only.
  • Cadence: nightly cron vs on-demand governed chat tool. Measure volume first.
  • Report surface: somewhere a human sees it, not a log line.
  • Scope: interactions only, or persons and chat mappings too.
Depends on

Nothing. Auto-correction is out of scope by ruling and stays a new owner decision.

Verdict

Do not run plan-it on this. Keep the five drift queries the measurement produced as a script in brain-scripts, re-run them weekly by hand or from a cron, and file one backlog card that names the 32 multi-match phones as the watch list. Promote to a program only if a re-run ever returns a non-zero count. The seed folder moves to 0-done with this measurement as its close-out.

The seed states that WhatsApp group message bodies are structurally not persisted: vector_data.text holds sender attribution only. The premise is false on the live path. Measured today on fernando-ott, message rows only, split by ingestion source:

The attribution-only rows are not a persistence gap. The connector composes group text as Group / From / displayText || text (normalize.ts:477-484), so a message with no text (a photo without a caption, a sticker, a reaction) writes no third line. The share is stable at 10 to 20 percent per day with no step change around any deploy, and it concentrates in one media-heavy group: Alimento Diário, 107 of 125 recent rows. Praxya has no WhatsApp connector and zero rows.

Why it matters now

Bodies for every group have been accumulating since 05-27 with no retention policy and no consent stance. That is the real privacy fact in front of you. hermes-studio S1 is no longer blocked on this; its group centre pane has content today.

Do we need it

A decision, yes, but a different one. Not store versus wall: the honest options are (a) keep storing and declare retention and PII posture, or (b) actively stop and purge, which is a removal with a migration, not a wall. Option (c) from the first draft of this page, scope storage to rooms the Secretário is pinned to or has adopted, is still on the table as a narrowing of (a).

One S-sized fix regardless: write the [image] / [audio] placeholder on the message row the way the thread parent already gets it, so a rooms UI does not render a blank turn for 12 percent of group traffic.
