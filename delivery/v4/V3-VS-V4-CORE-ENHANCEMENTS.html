plan-it v4 Blueprint

Nine core enhancements distilled from two months of runs, read against the v3 plugin as it ships today. Written for Fernando Ott, 2026-09-07. Every "v3 today" claim was checked against plugins/plan-it/; every "v4" item names the feedback that drove it.

v2 made the pipeline deterministic. v3 made the package hard to fake. What the field asked for next is different in kind: make the run legible to the human, and make it run end to end without them. Every note in delivery/v4 reduces to one of three shifts: from chat gates to HTML surfaces, from three interleaved gates to one up-front anamnesis plus one review-and-contradict round, and from "hand the package to one build session" to a planned build topology with named sessions and an autonomy contract.

The three shifts, at a glance

Shift 1 · surface

v3 speaks only markdown and chat. v4 keeps the markdown bundle as the AI-facing package and adds a human-facing report family (scope brief, decision queue, contract mirror, kickoff, handoff) rendered to local HTML by a deterministic renderer, the way conclude-it already builds its report.

Shift 2 · interaction

v3 interrupts three times (G1, G2, G3). v4 asks everything it will need up front (anamnesis), runs to a complete draft with recommended defaults applied, then presents one review-and-contradict round. Guided mode stays available.

Shift 3 · handoff

v3 ends in one KICKOFF and one launch prompt. v4 keeps both and adds: the build topology decided at G1 (solo, orchestrator + squads, headless), a session manifest with names and prompts, and a GATE autonomy contract so the build never wakes anyone.

The ten enhancements

Ordered by how much of the feedback each one absorbs. E1 to E4, E7 and E10 are the core of the release; E5, E6, E8 and E9 are the disciplines that make the core trustworthy. Each carries the words that asked for it.

E1

Explain before you ask: the scope brief

core
"once it starts it doesn't clarify what is everything in the output of the chat (only in the documentation, but I don't want to read all the documentation). The ideal is that before it prompt me with the decisions of the sizes for me to choose, it first explain what are the sizes what it involves and so on."Notion · Enhance plan-it · Lack of Clarity · with the G1 screenshot
v3 today

The G1 prompt offers "Size L, Shape 1 (Recommended)" and "Size M, leaner package" with one line each. What a shape is, how many documents it produces, how many sessions the build will need and how many times the human will be interrupted live only in references/templates.md.

The screenshot also shows plan-it narrating internals ("Rule 5 first", state file moves) that mean nothing to the person reading.

v4
  • Before the G1 question, render SCOPE-BRIEF.html: for each candidate size and shape, what it produces (file tree), what the build will look like (sessions, waves), what it costs the human (gates and the questions each will ask), and a plain sentence on when it is the wrong choice.
  • The chat prompt keeps the numbered options but each option's description is written for the reader, not the machine, and links the brief.
  • A legend rule for the whole run: every chat message that introduces a term (G1, shape, [REAL], INV, freeze) explains it once in that message.

What it changes for you: you choose a size knowing what you are buying, in the chat, without opening the reference docs.

E2

The HTML report layer, rendered deterministically

core
"We need a human UI summary." · "Great example on HTML." · "A few other htmls." · "Contract HTML."Notion · four headings, nine pointers, all of them local HTML files in Engine-Core
v3 today

Everything is markdown, and the final report is a chat message: "per-doc + per-epic status, total test count, the locked decisions, and the launch prompt". Reading a 158-case package means opening a dozen files.

v4
  • A report family, each with a markdown twin as the canonical source: SCOPE-BRIEF (E1), RESEARCH-REPORT (findings with measurements), DECISIONS (E3), CONTRACT mirror with the G2-locks banner, KICKOFF with the session manifest (E4), and PLAN-REVIEW (E7).
  • Rendering is a script, not the model: a JSON manifest authored by a low-tier model, rendered by scripts/build-report.mjs in the same manifest → template pattern as conclude-it/build-report.py. Zero npm dependencies, light/dark tokens, embedded markdown as collapsed toggles, mermaid where a flow is declared.
  • A gate-check mirror extension asserts the HTML was rendered from the current markdown; drift fails the handoff.
  • Standing rule carried from the orchestrator session: reports are local files opened in Chrome, never published artifacts.

What it changes for you: one page per gate, readable on a phone, with the evidence one click away. The determinism the pipeline has at the core reaches the surface you read.

E3

The decision queue replaces the decision list

core
"If the plan identify other decisions, actions blockers that depend on me, it should be in the plan html report so I can answer and the build-it can run autonomously until the conclude of it."Notion · A new way of planning · quoted /plan-it request
v3 today

Phase 7 collects judgment calls into "06 §4 Decisions only you can make", numbered, each with a recommendation, answered in chat. Locked answers are written back into the docs with owner and date. Actions and blockers that depend on the human have no home of their own.

v4
  • DECISIONS.md + .html modelled on DECISIONS-bkp-case.html: a ruled table (ID, ruling, effect on the waves), open cards each with the question, the recommendation, why nobody should pick for you, and a Read more that embeds the source note.
  • Three item kinds, because they are answered differently: decisions (pick an option), authorizations (grant or refuse a class of action, like praxya's dummy-Meta-writes grant), and owner actions (things only you can do: enter a key, approve a console). Owner actions carry a deadline relative to the waves they block.
  • Answers persist as a rulings table that every later report opens with ("Your rulings" in SEED-DECISIONS-v2), so a v2 of any report shows what you already decided.
  • The answered queue becomes GATE.md, the autonomy contract the build reads (E4).

What it changes for you: one page tells you what is waiting on you, what each answer unblocks, and what happens if you answer nothing. The build stops asking at 3am.

E4

Build topology is a planning decision

core
"Take in mind that we will run this with the orchestrator session approach, and the plan should determine all other sessions should I open, the name of other sessions so the orchestrator session can manage over night." · "kind of a new format that the plan should ask for which build format we want to plan."Notion · A new way of planning
v3 today

The handoff targets one fresh /build-it session: KICKOFF.md plus one copy-paste launch prompt. praxya's six-session KICKOFF, the sessions table in its program plan, and its orchestrator runbook were all authored ad hoc inside that run and never fed back into the plugin.

v4
  • G1 gains a third axis beside size and shape: topology. Options: solo (one build-it session, the v3 default), orchestrator + squads (one conductor plus one session per repo lane plus a QA session), headless overnight (conductor drives claude -p workers; the fallback the closeout night needed when a terminal stuck).
  • KICKOFF.md and its single copy-paste launch prompt stay exactly as in v3 (the solo path, and the orchestrator's own entry point). Topology adds to them, never replaces them.
  • SESSIONS.md: exact session names (used by /rename so the ledger and cross-session addressing work), role, what each reads, opens-when, and one launch prompt per session. Squad prompts name the orchestrator as the only address for contract contradictions.
  • The orchestrator runbook becomes a template: dispatch by wave, verify on disk, merge and deploy per CONTRACT, amend centrally, usage-limit wakeup chain, reap at wave close, morning report. Two lessons from the closeout night go in as standing rules: worktrees-only for any repo another session may touch, and deploys versus live squad runs are a collision class the conductor tracks.
  • Squads flag build-order corrections back into KICKOFF (praxya: "C1 → C3 → C2 → C4 → C5").

What it changes for you: you open N terminals, paste N prompts, go to sleep. The plan already decided who talks to whom.

E5

Show it, don't describe it

discipline
"I need in the report a visual mockup of each part that you try to explain. this is not so clear to me yet. also real usecases examples might help." · "I need a visual proposal, as mockup or mermaid flow for me to better understand."Notion · Great Report explaining why · Fernando's follow-up on SEED-TRIAGE
v3 today

Findings must cite path:line; confusing workflows must get a state model in the CONTRACT. Nothing asks for a picture, a mockup, or a use case a human can recognise. The triage report that prompted the quote was already good by v3's rules and still left you unconvinced.

v4
  • Report rule: every UI-shaped item ships a mockup drawn with real measured rows (SEED-DECISIONS-v2 drew the Salas pane from 8,510 WhatsApp rows and 89 transcripts, and said which text it had not read).
  • Every flow-shaped item ships a mermaid diagram of the mechanism, not the org chart.
  • Every proposal carries at least one real use case in the reader's words ("When the Secretário sends a message, the row should say Secretário, not Você").
  • Every surface enumerates its honest states: the good case, the legitimately empty case, the misconfigured case. When the system cannot answer the question a control implies, the control is removed, not the copy softened.
  • The renderer (E2) has first-class blocks for mockup, flow, use-case and states, so the model fills slots instead of inventing layout.

What it changes for you: you judge a proposal by looking at it. Prose stops being the only place a bad idea can hide.

E6

Triage before you plan, measure before you assert

discipline
"Seven seeds, four plans. Three read-only measurements ran on the live tenants after the first draft of this page. They moved three verdicts." · "Measured zero, skip the plan."SEED-TRIAGE-2026-09-04.html
v3 today

Invocation implies a plan. Phase 1 locks a DoD for the planning job; there is no verdict step that can conclude "do not run plan-it on this". Live grounding exists (Rule 4) but as a pre-freeze check, not as report content that can refuse a premise.

v4
  • A triage state before dodLock with four verdicts: Plan now, Build instead (already planned and frozen elsewhere), Owner decision, not a build, Skip (premise false or measured zero). Skip and Build-instead end the run with a one-page memo and a backlog card, not a package.
  • Multi-seed intake: N seeds in, one triage page out, then the surviving runs' G1s presented together so you answer once.
  • Measurement blocks in every report: the number, where it was read, when, read-only. A finding an agent could not re-verify is flagged where it appears ("one agent fabricated a finding. It is corrected in place and flagged").
  • Stale-fact detection is a named check: a seed that assumes a dependency is unbuilt when the board says 8/8 VERIFIED gets a "Stale fact" badge, and G1 sizes against the real state.

What it changes for you: planning effort goes only where the data agrees it should. A program you should not run becomes a paragraph, not a package.

E7

Anamnesis first, then one review-and-contradict round

core
"do the research on codebase, documentation, chrome CDP if necessary → anamynesis → use it own recommendations and create the entire plan end-to-end, and then a html report with the recommendations and then the user answer and contradict if he sees a problem in the plan." · "Before do the entire plan, the plan-it previously check everything that might need from the user so it can work end-to-end."Notion · New extra behaviour
v3 today

"Guided, with autonomous bursts": the run stops at G1, again at G2 after specs are drafted, again at G3 before the split. Each stop is a chat prompt. If you are away, the run parks. Decisions the model could have defaulted wait for you anyway.

v4
  • Anamnesis (new state after intake): a single batched questionnaire of everything the run may need from you: access and credentials it will probe, fences, naming preferences, topology, authorizations for live probes (CDP, read-only DB), and the decisions it can already see are yours. Answered once, up front.
  • Autonomous-draft mode: with anamnesis answered, the run proceeds through discovery, spec, decisions and the delivery split without stopping. Every decision gets the recommended default applied and marked "default, contradict if wrong". The CONTRACT is drafted, not frozen.
  • PLAN-REVIEW.html: one page with the complete draft package summarised, every applied default listed with its alternative, the risks, and the open owner actions. You contradict by number. A coherence pass threads the contradictions through; then the contract freezes and G3 is implicit.
  • Guided mode (the v3 three gates) remains selectable at anamnesis for work where your judgment is the input at every step.

What it changes for you: you spend ten minutes at the start and twenty at the end, not three interruptions in between. The plan arrives whole.

Trade-off to state plainly: applying defaults means the model decides things v3 refused to pre-decide (Rule 2). The guard is that every default is visible in one place with its alternative, nothing irreversible executes during planning, and the contract does not freeze until you have seen the review page. The rule becomes "batch and surface", not "never decide".
E8

Residual disposition so epics can close honestly

discipline
"Mainly at the end it learned one adaptation when we decide to move to backlog small items so we can close the epic."Notion · pointing at done-open-sessions-closeout-aug26-orchestrator · state file: backlog 33 → 19 accounted (10 parked-with-reason) → 3 with exact exit criteria
v3 today

The Test Contract is binding: 100% or iterate; an unreachable [REAL] case is IMPLEMENTED-NOT-VERIFIED. The status vocabulary is closed to four terms. What to do with small findings that are not contract cases is undefined, so overnight runs either hold the epic or invent a fifth status.

v4
  • CONTRACT and STATUS gain a residual disposition section: every non-green item at epic close is one of backlog-with-reason (a filed note with an exact exit criterion), owner-gated (waiting on a named human action), or INV (a contract case with an unreachable target). Nothing else is allowed.
  • An epic may close when all contract cases are VERIFIED or INV-with-reason and every residual has a disposition. Contract cases never move to backlog.
  • The orchestrator runbook (E4) includes the drain move: at wave close, sweep residuals into dispositions and report the counts, the way Wave 7 and Wave 8 did.
  • gate-check reconcile counts dispositions the way it counts cases: computed, never typed.

What it changes for you: a morning board that says "closed, 3 residuals filed with exit criteria" instead of an epic held open for a typo.

E10

Readable acronyms and a glossary

core
"The user doesn't understand something like 'I will do the A1, A2 then E1 and finally go back to R5 based on X3'. You need to explain what these means. Yes it is important for the AI and for us to have the acronyms but with explanation. A glossary would be good."Fernando · ruling on this report · 2026-09-07
v3 today

IDs are the grammar of the package (S1-A1, T-E1-06a, G-3, CB-n, D4, W2) and gate-check lints them for coherence. Nothing requires that a human-facing sentence expand them. Chat messages read like the screenshot: "Rule 5 first", "dodLock", "G1: Scope".

v4
  • First-use rule for every human-facing surface (chat messages, HTML reports, KICKOFF, DECISIONS): an ID or acronym is written with its meaning the first time it appears in that message or page. "S1-A1 (the scoped-settings collections epic)" then "S1-A1" after.
  • Glossary as a deliverable: GLOSSARY.md generated from the package (every epic ID, case prefix, gate, wave, squad, governance rule and status term with one line each), embedded as a collapsed panel at the top of every HTML report and linked from KICKOFF.
  • IDs stay exactly as they are in the markdown, because the AI and the gate-check lints need them. The renderer expands them; the model does not have to remember to.
  • gate-check handoff gains a check: every ID that appears in KICKOFF or DECISIONS resolves to a glossary row. Unknown ID fails the lint.

What it changes for you: you can read any page or chat message cold. The IDs keep working for the machines.

D1

Default interaction mode. Autonomous-draft (anamnesis + one review) or guided (the v3 three gates) as the default when the user does not say.
